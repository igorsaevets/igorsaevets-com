HTTPX2: cookies sent although the program had refused them

A bug report that led a maintainer of Pydantic's HTTPX2 to reopen and merge a fix closed 20 days earlier

Reported 23 November 2026 · fixed 24 November 2026 · code by a project maintainer · not yet in a published version

The software

HTTPX2 is free, open-source software for programs written in the Python programming language. It sends a program's requests to websites and web services and receives their replies. Pydantic, the organization behind the Pydantic library for Python, maintains it as the continuation of HTTPX, an older library of the same kind whose own development had slowed (the project's description).

The official Python library of the Model Context Protocol (MCP), the common standard for connecting AI assistants to tools, depends on HTTPX2: its current version, 2.3, requires it (the library's package file), as has every version since 2.0 in July 2026.

How widely it is used

  • HTTPX2 was downloaded 111,503,278 times from PyPI, the public registry of Python software, in the week of 21–27 November 2026.
  • On GitHub it has 1,691 stars (28 November 2026).

Download counts include automatic installs by build servers, so they show how much the software is used, not how many people use it. A GitHub star is a bookmark a user gives to a project.

The problem

Websites ask the programs that visit them to keep small pieces of data called cookies and to send them back with later requests; a cookie can, for example, keep a user logged in. A program that uses HTTPX2 can give it a cookie policy: a rule for which cookies it may keep and send back. A server that makes requests for many users through one shared HTTPX2 client, the part that sends the requests, can set a rule that refuses all cookies, so that a cookie meant for one user never goes out with another user's request.

That rule was lost when the program handed its cookies to HTTPX2 inside HTTPX2's own cookie container, called Cookies: HTTPX2 copied the cookies into a new container and left the rule behind. This happened on the ordinary way of giving a client its cookies, when the client is created, and also when they are replaced later. In my test the rule refused every cookie, yet a cookie set by one reply was sent with the next request.

What I did

I found the problem in an MCP server I was building, which shares one HTTPX2 client between its users: my test saw a cookie from one user's reply go out with the next user's request. On 23 November 2026 I reported it in the project's discussion forum, where its contribution guide asks for possible bugs to be raised (discussion #1359). The report gave a short script that shows the problem and its output, pointed to the lines of HTTPX2's code where the rule is dropped, and answered the reasons that had been given for closing an earlier fix (below).

What happened

  1. 4 November 2026, before my report. A maintainer of HTTPX2 had written a one-line fix that keeps the rule when cookies are copied (pull request #1314) and closed it unmerged the same day. The reasons given: the fix has to read an internal part of Python's own cookie code; the rule was lost only on a path the project had already deprecated, that is, marked to be phased out; and “no one has reported this”.
  2. 23 November 2026. My report showed the rule lost on the ordinary path, which is not deprecated. It also pointed out that Requests, another Python library of this kind, reads the same internal part when it copies cookies. About an hour later another outside contributor reproduced the problem and posted the same one-line change in the discussion.
  3. 24 November 2026, 23 hours after my report. The maintainer reopened the closed fix and merged it into the main code (commit 538b256).
  4. Release. As of 28 November 2026 the fix is not yet in a published version: the latest, 2.16.2, was published on 16 November, before it was merged.

How my report and the fix are connected

The maintainer did not reply in my discussion, and the pull request does not mention it, so the connection rests on the record above. The fix had been closed because the loss seemed limited to a deprecated path and no one had reported it. My report showed it on the ordinary path and answered the other reason. Twenty-three hours later the same fix was reopened and merged. I found no other report of this problem in the project's issues or discussions between those dates.

Who wrote the code

The code is the maintainer's: the fix written on 4 November, reopened and merged on 24 November. My part was finding the problem on the path the project still supports, showing it with a script, and answering the reasons the fix had been closed. Another outside contributor posted the same one-line change in the discussion.
